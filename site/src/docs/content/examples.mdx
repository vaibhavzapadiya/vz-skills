## A feature in a high-risk area

Request: `add rate limiting to the login endpoint`.

The path matches `auth|login`, so the tier is **high**. The route is `clarify → plan → implement → test → review → security-review → verify`, and the plan waits for your go-ahead.

```text title="/plan"
Plan: Rate limit /login   Risk: high   Profile: BALANCED   Depth: standard
Approach: reuse the existing express-rate-limit middleware pattern from /api/export
          (rejected: custom in-memory counter because it already exists as a dependency)
Slices:
  S1 limiter middleware - files: src/auth/rateLimit.ts, tests/auth/rateLimit.test.ts
     verify: pnpm test -- rateLimit - stop when: 6th request in a minute returns 429
  S2 wire into /login   - files: src/routes/login.ts
     verify: pnpm test -- login - stop when: existing login tests still green
Criteria coverage: AC1 -> S1,S2; AC2 -> manual (NOT VERIFIED)
Risks/guardrails: auth path => security-review mandatory in verify
Rollback: revert the two files; no schema or config change
Next: implement S1 (high risk: waiting for your go-ahead)
```

Reply with your go-ahead and the work proceeds slice by slice. The final report is the evidence table shown in [Getting started](/docs/getting-started#what-a-first-result-looks-like).

## A failing test

Request: `/debug the checkout test fails with "expected 3 received 2"`.

`debug` reproduces the failure and walks the stack to the first repository frame. It tests at most three hypotheses, each with evidence, and confirms the root cause with a test that fails for that reason. Only then does it hand a minimal fix plan to `implement`. If the failure appears in the baseline, it is reported as pre-existing and not fixed inside an unrelated task.

## Reviewing a branch

```text
/review branch
```

`review` diffs the branch against its base, maps each acceptance criterion to the hunks that satisfy it, flags unrelated hunks as scope creep, and runs cheap checks that discovery confirmed. In BALANCED it delegates to the independent reviewer on medium or high risk and runs `/security-review` if the diff touches sensitive paths. For a pull request use `/review 123`, which needs the `gh` CLI; without it the step is reported BLOCKED with the reason.

Findings come back ranked:

```text
blocker  src/auth/session.ts:88   token compared with == instead of a constant-time compare
major    src/routes/login.ts:41   new branch has no test (AC2 NOT VERIFIED)
minor    src/auth/rateLimit.ts:12 name shadows the imported limiter
Verdict: request changes
```

The identifiers above are illustrative of the format; real findings cite your files.

## An unfamiliar repository

```text
/discover
```

Read the Unknowns first. If the test command is `UNKNOWN`, tell the skill the command or add a script to the manifest. To record pre-existing failures before touching anything:

```text
/discover --baseline
```

The baseline runs only if the detected test command is on the allowlist; otherwise it is `BLOCKED` and says why.

## A release check

```text
/release 0.2.0
```

`release` freezes scope, runs full verification, audits dependencies, drafts the version bump and changelog, inspects the artifact, writes a rollback plan, and gives a go or no-go. Tagging, pushing, and publishing happen only when you say so, one step at a time.

## A long task, handed over

Before context runs out, or before you stop for the day:

```text
/checkpoint save
```

The checkpoint file records the criteria, each slice with its status label and evidence, the last commands with their results, dirty files that are not yours, blockers, and one next exact action. It contains no secrets: it references locations, not values. Add `.vz-skills/checkpoint.md` to `.gitignore` if the task is personal.

In a new session, or after a teammate takes over:

```text
/checkpoint resume
```

Resume reports each drift explicitly, for example that HEAD changed or that a check now fails, re-runs the last narrow check, and downgrades labels the repository no longer supports. It then continues from the first slice that is not VERIFIED.

When the work is verified, hand it on:

```text
/standup yesterday
/pr main
```

`/standup` summarises git history, the working tree, and the checkpoint. `/pr` writes the title and description from the `verify` evidence and prints the `gh pr create` command. It creates the pull request only when you ask, and `approvals.external_actions: "refuse"` means it never does.

## Raising rigor for one session

Set the profile through the environment without editing files:

```bash
VZ_SKILLS_PROFILE=PRODUCTION claude
```

The variable overrides `profile` only; every other key still comes from your config files. On PowerShell use `$env:VZ_SKILLS_PROFILE = 'PRODUCTION'` before starting `claude`.

## Protecting a directory

```json title=".vz-skills/config.json"
{
  "version": 1,
  "profile": "BALANCED",
  "hooks": { "protected_paths": ["migrations/**", "infra/**"] },
  "approvals": { "destructive_git": "refuse" }
}
```

Writes to `migrations/` and `infra/` now ask, `rm` and `mv` on them ask, and destructive git commands are denied instead of asked. Anything in those paths is also treated as high risk. Check the effective result with `/vz-status`.
