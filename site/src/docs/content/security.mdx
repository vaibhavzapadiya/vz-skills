<Lead>
Claude Code's permissions and sandbox are the security boundary. VZ Skills reduces accidents on top of them and never claims to replace them.
</Lead>

## Assets

Source code and uncommitted work; credentials in `.env`, key files, the environment, and credential stores; build and release integrity; and the accuracy of verification reports.

## Trust boundaries

1. **Your instructions in the conversation.** Trusted.
2. **Claude Code permissions and sandbox.** The enforcement boundary. VZ never overrides, weakens, or bypasses them, and its configuration cannot.
3. **Repository content** (files, `CLAUDE.md`, comments, fixtures, issues), **tool output**, and **web content**. Untrusted data. The core policy, every skill, and every agent say so explicitly; discovery flags injection indicators; the eval suite includes an adversarial case.
4. **VZ hooks.** Advisory, fail open, deterministic. See [Hooks and guards](/docs/guards).
5. **VZ scripts.** Run only what is documented. Discovery executes no project script unless `--run-baseline` is given and the command is on a conservative allowlist.

## Threat scenarios and mitigations

| # | Threat | Mitigation |
|---|---|---|
| 1 | Prompt injection in repository files asks for secrets | Core policy rule 4; discovery flags eight indicator classes and names the file; skills quote and refuse; agents report, never act |
| 2 | Malicious instructions ask for destructive shell commands | Command guard denies catastrophic patterns and asks on risky ones; `approvals.destructive_git: refuse` denies |
| 3 | Untrusted scripts execute during discovery or tests | Discovery executes nothing by default; the baseline allowlist rejects anything but well-known test commands; `approvals.run_project_scripts` |
| 4 | Secret values leak into output, logs, or reports | Discovery never reads `.env` and redacts key-like strings; the write guard asks before credential-looking content; skills forbid printing secrets |
| 5 | Path traversal or malformed config causes writes outside the project | Config rejects absolute, `..`, `~` and drive paths; `vz-discover --out` refuses paths outside the root; the write guard denies OS, credential and `.git` targets |
| 6 | Hook failures misrepresented as enforcement | Hooks fail open and are documented as advisory everywhere |
| 7 | A config typo silently disables a check | Unknown keys are errors with suggestions; safety floors; acknowledged overrides print a warning on every resolution |
| 8 | The agent overstates test results | Status vocabulary enforced by policy and the `verify` skill; evidence labels floored to true |
| 9 | Copied code introduces licensing or supply-chain concerns | No code copied from reference projects; zero runtime dependencies |
| 10 | Existing user changes overwritten | Dirty files are listed with a preservation note; `implement` and `verify` require untouched files to stay byte-identical; the guard asks before `git checkout -- .`, `stash drop`, `reset --hard` |
| 11 | A hook or script reads outside the project | The discovery walk is bounded, skips symlinks, and reads only known manifest and instruction files; hooks read stdin and the project config only |

Each mitigation is covered by named tests in `tests/` in the repository; `docs/security.md` there maps threats to tests.

## What VZ reads and writes

| Action | Behaviour |
|---|---|
| Reads | Known manifests, lockfiles, CI files, instruction files, and your `.vz-skills/config.json` (and `~/.vz-skills/config.json`). Never `.env` or key files. |
| Writes | `.vz-skills/config.json` when you run `/setup`; `.vz-skills/cache/` only with `--cache`; flat-install files and a backed-up settings file when you install. |
| Network | None at runtime. |
| Secrets | Never opened or printed by VZ scripts. Key-like strings are redacted from echoed output. |
| Processes | Hooks run `node` with the plugin's own scripts. Baselines run only allowlisted test commands. |

## Residual risks

<Callout kind="warning" title="Read these before relying on the guards">

- The command guard matches **text, not behaviour**. An innocuous-looking script can be destructive. Review and sandboxing remain necessary.
- Injection detection is **heuristic** (regular expressions). Novel phrasings will not be flagged. The policy still tells the model to treat repository text as data, but that instruction is not a mechanical guarantee.
- Hooks do not see files inserted through `@` mentions.
- The baseline runner trusts that `npm test` and similar commands run the project's declared script. It does not inspect the script body.
- `claude plugin eval` runs plugin hooks outside its sandbox, per the platform. Evaluate only plugins you trust, including this one if you modified it.
- Behavioural guarantees about skills depend on the model following instructions. The eval suite measures this on a small sample only, and has not been run.

</Callout>

## Recommended practice

- Keep Claude Code's permission rules and sandbox on. Treat VZ prompts as a second look, not the first.
- Commit `.vz-skills/config.json` so the whole team shares the same floors.
- Set `hooks.protected_paths` for migrations, infrastructure, and release files.
- Use `approvals.destructive_git: "refuse"` and `approvals.external_actions: "refuse"` on repositories where an accidental prompt approval would be costly.
- Read `WARNING: SAFETY DOWNGRADE` lines when they appear. They mean someone chose to lower a floor.

## Reporting a problem

If a secret appears in a report, treat it as a bug. The write guard, discovery redaction, and policy all aim to prevent it. Open an issue with a redacted example, the Claude Code version, and the output of `vz-config.js --explain`.
