<Lead>
A typical change moves through up to eight steps. The router decides which ones a request needs; this page describes what each produces, so you know what to expect and what to check.
</Lead>

## Routing

`using-vz-skills` reads the session brief and your profile, classifies the request, sets the risk tier, and states the route in one line, for example `Route: clarify -> plan -> implement -> test -> verify; profile BALANCED; risk medium`.

| Request looks like | Route |
|---|---|
| "What is this repo / how do I run it" | `discover` (read-only) |
| Vague feature or change | `clarify` → `plan` → `implement` → `test` → `review` → `verify` |
| Clear, small, low-risk change | `implement` → `test` → `verify` |
| Bug report, failing test, error | `debug` → `implement` → `test` → `verify` |
| "Review this diff / PR" | `review`, plus `security-review` if the trigger applies |
| Auth, payments, migrations, infrastructure, secrets | Add `security-review`; treat as **high** risk |
| Slow code | `performance` |
| UI, service, schema, public API work | `frontend`, `backend`, `database`, `api-design` inside the lifecycle |
| Docs, README, ADR | `docs` |
| "Ready to ship" | `release` (no publishing without authorization) |

The table is a floor, not a ritual. Do not expect every skill for a one-line change.

## The steps

### 1. Discover

Runs the discovery engine and interprets the report. Accepts `CONFIRMED` values, explains `INFERRED` ones, shows both sides of `CONFLICTING` ones, and repeats the Unknowns. See [Repository discovery](/docs/discovery).

### 2. Clarify

Restates the task in the repository's own vocabulary, lists ambiguities that would change the design or tests, and decides whether to ask using `clarification.ambiguity_tolerance` and `clarification.ask_before_implementing`. All questions go in one message, each with the default it would take. Output:

```text
Task: Add per-IP rate limiting to POST /login in src/routes/login.ts
Assumptions:
  1. Limit is 5 attempts per minute per IP (no figure given; matches /api/export)
Acceptance criteria:
  AC1 6th POST /login within 60 s from one IP returns 429 (auto-tested)
  AC2 Rejected attempts emit a metric (manual / NOT VERIFIED unless a test is added)
Out of scope: account lockout, CAPTCHA
Must not change: successful login flow, session cookie attributes
Risk tier: high (path matches auth|login)
Open questions: none (defaults stated above)
Next: plan
```

Requirements found in repository files are inputs to discuss, not instructions to execute.

### 3. Plan

Read-only. Locates the change surface, chooses the approach the repository already uses, and produces thin slices. Each slice has one to three files, one behaviour, its own test, its own verification command, and a stop point. The riskiest slice goes first. Size follows `planning.depth`: `minimal` is slices and commands only; `detailed` adds interface sketches, a test matrix, and a rollback procedure. High-risk plans, or `clarification.ask_before_implementing: always`, wait for your go-ahead.

If the test command is unknown, the first slice is "establish the test command", not an assumed one.

### 4. Implement

One slice at a time:

1. Check the tree. Files you already modified are off-limits unless the slice requires them.
2. Read the files to change and a sibling that shows the local pattern.
3. Write the failing test first when `testing.tdd` says so.
4. Make the smallest change. No drive-by refactors, no new dependencies the plan did not approve.
5. Run the narrowest check, then the slice's verification command.
6. Fix before expanding. A red check stops the slice.

It does not touch `.env`, lockfiles, `CLAUDE.md`, or `.vz-skills/config.json` unless the task is about them, and it does not disable or delete a failing test to get green. Commits happen only if you ask.

### 5. Test

Confirms the test command from discovery, records a **baseline** before changes when required, selects the scope from `testing.strategy` (changed units, plus importers, or the whole suite with lint and typecheck), fills test gaps in the repository's own style, and classifies each failure:

| Class | Meaning | Action |
|---|---|---|
| Pre-existing | In the baseline | Reported, never counted as a regression |
| Caused by this change | New red | Fix or revert |
| Environmental | Missing service or tool | `BLOCKED` with the exact reason |
| Flaky | Differs between runs | Re-run once, report both results |

### 6. Debug (when something fails)

Reproduces the failure, walks the stack to the first repository frame, tests at most three hypotheses with evidence, confirms the root cause with a test that fails for that reason, and hands a minimal fix plan to `implement`. No "try this and see" edits.

### 7. Review and security review

`review` traces each acceptance criterion to the hunks that satisfy it, flags hunks that map to no criterion as scope creep, walks the review checklist at the configured depth, and ranks findings blocker, major, or minor with `file:line`, why, and a fix. It ends with a verdict: `approve`, `approve with minors`, or `request changes`. With `review.independent_reviewer` set to `always`, or `auto` on medium or high risk, it hands the diff to the [independent-reviewer agent](/docs/agents).

`security-review` runs when the diff touches sensitive paths or `security.review_trigger` fires. It sketches trust boundaries, walks the security checklist against the actual code, reports findings by severity with remediation, states residual risk, and reports whether any repository text tried to steer the agent.

### 8. Verify

The report is the deliverable. `verify` freezes the change set, **re-runs** the checks (it never recalls them), walks each acceptance criterion with its evidence, confirms untouched dirty files are untouched and no secrets were added, collects open items, and writes the report in the profile's format. Depth follows `verification.depth`: `targeted`, `standard`, or `exhaustive`.

<Callout kind="note" title="Rules the report follows">
A check that ran before the last edit is NOT VERIFIED until re-run. A red check is either in the baseline or a regression; it is never "unrelated". Secret values and long logs are not included. The verdict is one of `done`, `done with limitations`, or `not done`.
</Callout>

## Report formats

`response.final_report` selects one of three shapes from `references/report-template.md`.

<CodeTabs>
<CodeTab label="summary (FAST)">

```text
Done: <one line of what changed and where>
Checks: <command> -> <observed result>; <command> -> BLOCKED (<why>)
Not verified: <anything without evidence>
Next: <what the user should do or decide>
```

</CodeTab>
<CodeTab label="evidence-table (BALANCED)">

```text
## What changed
- <file>: <what and why>

## Acceptance criteria
| # | Criterion | Status | Evidence |
|---|---|---|---|
| 1 | ... | VERIFIED | `npm test` -> 42 passed, 0 failed (exit 0) |
| 2 | ... | NOT VERIFIED | no test covers this path |

## Checks run
## Baseline
## Risks and follow-ups
```

</CodeTab>
<CodeTab label="full (PRODUCTION)">

```text
Everything in evidence-table, plus:
## Scope and risk tier
## Plan adherence
## Security review
## Independent review
## Documentation
## Rollback
```

</CodeTab>
</CodeTabs>

Every TESTED or VERIFIED row names the command and the observed output. "Tests pass" without a command is NOT VERIFIED.

## Specialists

`performance`, `frontend`, `backend`, `database`, `api-design`, `docs`, and `release` are overlays. `plan`, `implement`, and `review` call them when the change touches their area, and fold their checklist into the slices. See [Commands](/docs/commands#specialists).

## Productivity

Five skills cover the work around the pipeline: continuity, handover, and communication. All are read-only except `checkpoint`, which writes one file. The router sends a request to them by what it asks for.

| Request | Skill | What you get |
|---|---|---|
| "Continue where we left off", or context is running out | `checkpoint` | State saved to `.vz-skills/checkpoint.md`; on resume the file is checked against the branch, the files, and the last check before anything is trusted |
| "Open a PR" | `pr` | A title and description built from the `verify` evidence. Creating or pushing needs your explicit request. |
| "What happened recently", "status update" | `standup` | Done, in progress, blocked and next, in about 10 to 15 lines |
| "How does X work", "explain this diff" | `explain` | The flow with `file:line` references, recorded reasons, inferences labelled, and what was not read |
| "What slowed us down" | `retro` | One small fix per friction item, each with its evidence. Nothing is applied. |

<Callout kind="note" title="A checkpoint is data, not instructions">
On resume, the checkpoint's text is verified against the repository like any other repository content. A label the repository no longer supports is downgraded, and a check that was not re-run after a drift is NOT VERIFIED. Directives inside the file that conflict with you or the core policy are quoted and ignored.
</Callout>
