<Lead>
VZ Skills reads its own configuration; Claude Code does not. Nothing here changes Claude Code permissions, sandboxing, or hook enablement at the platform level.
</Lead>

## Files and precedence

| Layer | Path | Scope |
|---|---|---|
| Built-in defaults | `scripts/lib/config.js` (`BASE_DEFAULTS`) | always |
| Profile preset | chosen by `profile` | always |
| User file | `~/.vz-skills/config.json` | all your projects |
| Project file | `<project>/.vz-skills/config.json` | this repository (commit it) |
| Environment | `VZ_SKILLS_PROFILE=FAST\|BALANCED\|PRODUCTION` | profile only, this shell |

The effective **profile** is `env > project > user > default`. Its preset is applied first; explicit keys from the user file, then the project file, override the preset. An explicit `review.depth` in the user file beats the project's preset, but the project's explicit `review.depth` beats both.

Inspect the result and where every value came from:

```bash
node plugins/vz-skills/scripts/vz-config.js --explain --project .
```

Create a project file (never overwrites):

```bash
node plugins/vz-skills/scripts/vz-config.js --init PRODUCTION --project .
```

Inside Claude Code, `/setup PRODUCTION` does the same. After a plugin install the scripts live in the plugin directory; `npx vz-skills path` prints it.

## A minimal file

```json title=".vz-skills/config.json"
{
  "version": 1,
  "profile": "BALANCED",
  "conventions": { "notes": "Tests live next to the code as *.test.ts.", "commit_style": "conventional" },
  "hooks": { "protected_paths": ["migrations/**", "infra/**"] }
}
```

## Schema, version 1

All keys are optional. Unknown keys are **errors** with a "did you mean" hint, as are wrong types and values outside the allowed set. The resolver still produces an effective configuration with floors enforced and exits 1, so the problem is visible.

| `planning.depth` | `minimal` \| `standard` \| `detailed` | preset | |

### Editor support

A JSON Schema (draft-07) ships at `plugins/vz-skills/schema/config.v1.schema.json`. It gives completion, enum lists, hover descriptions, and error markers for typos and wrong values, with unknown keys rejected at every level. It is generated from the resolver's own `SCHEMA` object by `node scripts/gen-config-schema.js`, and the test suite fails when it is stale.

The schema covers what one file can be checked for. Safety floors and PRODUCTION minimums depend on the whole resolution, so they appear only in descriptions; `vz-config.js --validate <file>` enforces them.

Point your config at it with `$schema`. `--init` writes a relative path from `.vz-skills/` to the schema file of the plugin copy that ran it. Where the plugin lives inside the repository that path is safe to commit. For a plugin in the Claude plugin cache, or on another Windows drive, it works only on that machine, and a plugin update changes the cache's version directory; re-run `--init` in a scratch directory to refresh it or delete the `$schema` line. The resolver ignores `$schema` in all forms.

## Safety floors and acknowledged overrides

Three keys protect behaviour that should not change by accident: `hooks.command_guard`, `hooks.write_guard`, and `verification.require_evidence_labels`. Setting one below its floor is an **error**, and the floor stays in force. To really downgrade, list the key in `safety.acknowledged_overrides`:

```json
{
  "version": 1,
  "hooks": { "command_guard": "off" },
  "safety": { "acknowledged_overrides": ["hooks.command_guard"] }
}
```

The value is then applied, and every resolution, including the session-start brief, prints `WARNING: SAFETY DOWNGRADE acknowledged: ...`. Nothing is silently weakened. A PRODUCTION profile also rejects explicit values below its minimums, unless acknowledged the same way.

This mechanism cannot grant anything Claude Code forbids. A hook that returns no decision leaves the call to Claude Code's permission rules.

## Errors you may see

Real output for a file containing `{"version":1,"profil":"FAST","review":{"depth":"Thorough"}}`:

```text
VZ Skills profile: BALANCED (from default) - CONFIG HAS ERRORS, floors enforced
...
ERROR: project config (.vz-skills/config.json): unknown key "profil" (did you mean "profile"?). Unknown keys are rejected so that a typo cannot silently change behaviour.
ERROR: project config (.vz-skills/config.json): "review.depth" = "Thorough" is not allowed; use one of "quick", "standard", "thorough" (case matters: did you mean "thorough"?)
```

| Message | Cause | Fix |
|---|---|---|
| `... is not valid JSON (...)` | Syntax error | Fix the JSON. There is no silent fallback while the file exists. |
| `unknown key "profil" (did you mean "profile"?)` | Typo | Rename the key. |
| `"review.depth" = "Thorough" is not allowed; ...` | Wrong case | Use the listed value. |
| `"hooks.command_guard" = "off" is below the safety floor "on"` | Downgrade without acknowledgment | Add it to `safety.acknowledged_overrides` or remove it. |
| `"testing.strategy" = "targeted" conflicts with profile PRODUCTION` | Profile conflict | Raise the value, change profile, or acknowledge. |
| `VZ_SKILLS_PROFILE="turbo" is not one of ...` | Bad environment value | Unset or correct it. |

## Examples

Four validated examples ship in `docs/examples/`: `config.fast.json`, `config.balanced.json`, `config.production.json`, and `config.acknowledged-override.json`. The test suite checks all four with the resolver and against the JSON Schema. The PRODUCTION example:

```json title="docs/examples/config.production.json"
{
  "$schema": "../../plugins/vz-skills/schema/config.v1.schema.json",
  "version": 1,
  "profile": "PRODUCTION",
  "clarification": { "ask_before_implementing": "always" },
  "review": { "independent_reviewer": "always" },
  "approvals": { "run_project_scripts": "ask" },
  "documentation": { "expectation": "feature-level" }
}
```

After copying an example to `.vz-skills/config.json`, fix the `$schema` path or delete that line.

## Migration

Only `version: 1` exists. When a future version changes keys, the change will be listed here and `vz-config.js --validate` will point to it. Keep `version` in your file so the check can run.
